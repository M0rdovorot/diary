# Voice Bot — контекст проекта

## Что это
Личный Telegram-бот на Go: принимает голосовые сообщения, распознаёт речь через облачный API, делает структурированное саммари через облачную LLM.

## История решения (важно для контекста)
**перейти на облачные API**: **Yandex SpeechKit** для распознавания речи и **YandexGPT** для саммаризации. Причины выбора именно Яндекса:
- Оплата напрямую рублями (карта/СБП) без посредников и иностранных карт.
- Цена при объёме пользователя (~20 мин/день) минимальна в любом случае — экономия не была решающим фактором.
- Явных независимых сравнений качества распознавания/саммаризации на русском между провайдерами найти не удалось — выбор сделан по совокупности удобства, а не по строгим бенчмаркам.

Изначально пользователь выбрал **синхронный** режим SpeechKit (ради мгновенного ответа), но при проверке документации выяснилось, что синхронный режим ограничен 30 секундами аудио на запрос — для голосовых сообщений Telegram (которые часто длиннее) это неприменимо без нарезки на кусочки. После этого решили **перейти на обычный асинхронный режим** — см. решения ниже.

## Нагрузка
Один пользователь, ~20 минут голосовых в день суммарно, разово в день.

## Принятые решения по архитектуре (зафиксировано пользователем)
- **Режим Yandex SpeechKit: асинхронный обычный** (не синхронный, не отложенный/deferred).
  - Причина смены с синхронного: у синхронного режима жёсткий лимит **30 секунд аудио и 1 МБ на файл** (официальная документация SpeechKit) — не подходит для голосовых сообщений Telegram, которые часто длиннее. Асинхронный режим поддерживает файлы до 4 часов, что закрывает вопрос лимитов.
  - Ожидание ответа — не мгновенное (по документации асинхронная обработка может занимать от нескольких минут; точного SLA нет), но для сценария пользователя (бот обрабатывает голосовые в фоне, не в реальном времени при живом диалоге) это не критично.
  - Цена (справочно): ~0.61 ₽/мин, то есть ~366 ₽/мес при объёме 20 мин/день.
  - Важно: результаты асинхронного распознавания хранятся на сервере Яндекса только **3 дня** — бот должен успевать забирать результат (опрашивать статус операции и не затягивать).
- **Object Storage (бакет) обязателен.** Асинхронный SpeechKit принимает аудио не напрямую в теле запроса, а **по ссылке на файл в Yandex Object Storage**. Поэтому пайплайн такой: бот скачивает OGG из Telegram → загружает в приватный бакет (S3-совместимый API, статические ключи доступа сервисного аккаунта) → передаёт в SpeechKit ссылку (для приватного бакета — pre-signed URL) → опрашивает операцию → забирает текст. После обработки файл из бакета удаляется (плюс lifecycle-правило на автоудаление как страховка).
- **Версия YandexGPT: Pro.** Дороже Lite (~290 ₽/мес против ~48 ₽/мес при текущем объёме), но выбрана ради более высокого качества саммаризации. Разница в деньгах при таком объёме несущественна.
- **Деплой бота: через Docker.** Даже без тяжёлых локальных моделей (Whisper/Ollama больше не нужны) — для единообразия с будущими Postgres/Redis и простоты переноса между окружениями.
- **Сервер: конфигурация.** Текущий тариф Timeweb Cloud MSK 50 (4 CPU / 8 ГБ RAM / 80 ГБ NVMe)

## Стек
- **Backend:** Go 1.25, Telegram-бот через long polling на библиотеке **`github.com/go-telegram/bot`** (выбрана вместо `go-telegram-bot-api`: поддерживается, контексты и хендлеры из коробки) — без вебхука, чтобы не нужен был домен/SSL на старте.
- **STT (речь → текст):** **Yandex SpeechKit**, асинхронный обычный режим (модель `general`, не `deferred-general`), REST API.
  - Формат голосовых Telegram — OGG/Opus. **Проверено по документации:** OggOpus поддерживается во всех версиях API распознавания SpeechKit без ограничений — конвертация не требуется.
  - Цена: ~0.61 ₽/мин (~366 ₽/мес при 20 мин/день).
  - Результаты хранятся на сервере Яндекса только 3 дня — бот должен опрашивать статус операции и забирать результат вовремя.
- **Хранилище аудио:** **Yandex Object Storage** (S3-совместимое), приватный бакет — промежуточное хранилище для файлов, которые SpeechKit забирает по ссылке. Для доступа из Go — `github.com/minio/minio-go/v7` (endpoint `https://storage.yandexcloud.net`, статические ключи доступа; он же выдаёт pre-signed URL).
- **Саммаризация/извлечение:** **YandexGPT Pro**, REST API. Модель возвращает JSON по дням (поля — в разделе «Модель данных»), текст саммари для Telegram собирает код. Структура записи зафиксирована пользователем: дата, дневниковая запись от первого лица, настроение, питание, стул, сон, физическое состояние, работа, Катя, занятия (успел/не успел), привычки (вода, сладкое, алкоголь, курение, «гонение лысого», «занятие любовью», китайский чай), мысли на подумать, мысли для психолога. Отсутствующее не выдумывается (`null` → «не упоминалось»).
- **Postgres:** используется (история транскриптов, сегменты, наблюдения). **Redis:** не используется и пока не нужен.

## Оплата Yandex Cloud
- Способы: банковские карты (Мир, Visa, MasterCard), СБП — расчёты в рублях для резидентов РФ.

## Как работает код сейчас
Структура:
- `cmd/bot/main.go` — точка входа: конфиг → часы дневника → Postgres (+миграции) → клиенты Object Storage/SpeechKit/YandexGPT → хендлеры → long polling; корректно завершается по SIGINT/SIGTERM.
- `internal/config` — env. Обязательные: `TELEGRAM_BOT_TOKEN`, `ALLOWED_USER_ID`, `DATABASE_URL`, `YC_API_KEY`, `YC_FOLDER_ID`, `YC_BUCKET`, `YC_S3_ACCESS_KEY_ID`, `YC_S3_SECRET_ACCESS_KEY`. Необязательные (есть значения по умолчанию): `DATA_DIR` (`data`), `DATA_RETENTION_DAYS` (`7`), `DIARY_TZ` (`Europe/Moscow`), `DAY_CUTOFF_HOUR` (`5`), `YC_GPT_MODEL` (`yandexgpt/latest` = Pro), `YC_S3_ENDPOINT`, `YC_S3_REGION`. Прокси — обычные `NO_PROXY`/`HTTPS_PROXY` в `.env` (читают `make run` и docker compose). Для compose и бэкапов ещё `POSTGRES_PASSWORD`, `BACKUP_PASSPHRASE`.
- `internal/cleanup` — `Sweep`/`Run`: удаляет `*.ogg` старше срока хранения (при старте и раз в сутки).
- `internal/diaryday` — «день дневника» со сдвинутой границей (05:00 МСК): `LogicalDate(t)`.
- `internal/handler` — `handler.go`: приём voice, скачивание, распознавание, `processTranscript` (сохранить → `analyze`), `analyze` (извлечь → сохранить/заменить сегменты → ответить), `referenceDate` (рабочий день); `dates.go`: вопрос о дате кнопками, общее состояние текстового ввода (`pendingInput`: дата / замены / новый текст), `/pending`, `/day`, `/date`; `edit.go`: `/edit` и правка расшифровок.
- `internal/stt` — `storage.go` (бакет, pre-signed URL на 1 час, удаление), `speechkit.go` (API v2: `Submit` → `Wait` с опросом раз в 5 с).
- `internal/summary` — `prompt.go` (JSON-промпт, `PromptVersion = "json-v2"`), `yandexgpt.go` (клиент `foundationModels/v1/completion`, temperature 0.2, `x-data-logging-enabled: false`, `URL` переопределяется в тестах), `extract.go` (`Extract`: один повтор, если ответ не разобрался).
- `internal/entry` — `fields.go` (реестр полей и их типов), `parse.go` (разбор JSON модели, очистка заглушек «не упоминалось», `ResolvedDate`), `card.go` + `render.go` (слияние наблюдений в карточку дня, отрисовка с пометками источника), `userdate.go` (разбор дат пользователя: «05.09», «05.09.2026», «вчера»…).
- `internal/store` — `store.go` (пул pgx, встроенные миграции, `SaveVoice`), `extraction.go` (`SaveExtraction` / `ReplaceExtraction`: извлечение + сегменты + наблюдения одной транзакцией; `ExtractionInput`), `day.go` (`DayObservations`, `PendingSegments`, `ResolveSegment`), `voices.go` (`GetVoice`, `RecentVoices`, `VoicesForDay`, `UpdateTranscript` с историей правок, настройки `Setting/SetSetting/DeleteSetting`).
- `migrations/` — SQL-миграции, вшиваются в бинарник (`embed`), применяются при старте. `001_init.sql` — схема, `002_*` — `raw_response` как TEXT, `003_*` — `voice_messages.reference_date`, таблицы `transcript_edits` (история правок) и `settings`.
- `scripts/backup.sh`, `scripts/restore.sh` — шифрованные бэкапы (`pg_dump | gzip | openssl aes-256-cbc -pbkdf2`), ротация (`BACKUP_KEEP`, 14), восстановление в **новую** базу.
- `Makefile` — `run` (поднимает Postgres в Docker и запускает бота с `.env`), `build`, `vet`, `test` (с интеграционными тестами: создаёт БД `diary_test`, пакеты идут по очереди `-p 1`), `db-up/db-down/psql`, `backup`, `restore FILE=… [DB=…]`, `docker-up/down/logs`.
- `docker-compose.yml` — `db` (postgres:17-alpine, порт только на 127.0.0.1, healthcheck, volume `pgdata`) и `bot` (DATABASE_URL внутри сети compose подставляется сам).

Поток обработки одного голосового:
1. Приходит voice. Если отправитель не `ALLOWED_USER_ID` — игнорируется (warn в лог).
2. Бот определяет **день записи** (`reference_date`): выбранный командой `/date` рабочий день или, если он не выбран, день дневника на момент отправки (`logical_date`, граница 05:00 МСК). Скачивает OGG (таймаут 60 с) в `DATA_DIR`, отвечает «Голосовое получено, распознаю…» (если выбран рабочий день — с напоминанием о нём).
3. Файл → бакет (`voice/<имя>`), pre-signed URL → SpeechKit → опрос операции (общий лимит с загрузкой 30 минут); объект из бакета удаляется всегда. **После успешного распознавания локальный `.ogg` удаляется сразу**; при неудаче остаётся и подметается `cleanup` по сроку `DATA_RETENTION_DAYS`.
4. **Расшифровка сразу сохраняется в `voice_messages`** (до обращения к модели, чтобы ничего не потерять) вместе с `logical_date` и `reference_date`.
5. `analyze`: YandexGPT (таймаут 3 мин) возвращает JSON — сегменты по дням; опорная дата для «сегодня/вчера» — день записи. Не разобралось — один повтор, затем бот присылает сырую расшифровку и кнопку «Повторить разбор».
6. `SaveExtraction` в одной транзакции: `extractions` (сырой ответ), `segments`, `observations`. Сегмент с надёжной датой (названа, не позже дня отправки, не старше 2 лет) → `resolved`, иначе → `pending_date`. `relation` наблюдения: `same_day`, если дата сегмента = день записи, иначе `retro`. Если БД недоступна — бот всё равно показывает результат с пометкой «не удалось сохранить».
7. В чат — по сообщению на сегмент (текст собирает код, не модель). Для сегмента о другом дне — пометка «Запись о другом дне — добавлена в карточку этого дня». Для сегмента без даты — вопрос с кнопками «Сегодня / Вчера / Другая дата» (считаются от дня записи); если таких сегментов несколько, вопросы нумеруются («запись 2 из 3») и содержат выдержку из текста; «Другая дата» → ждём текст «ДД.ММ[.ГГГГ]». Пока дата не уточнена, сегмент в карточки не попадает; после перезапуска вопросы повторяются по `/pending`.

**Команды:** `/help` (и `/start`) — справка по всем командам и принципам работы (`internal/handler/help.go`, держать в актуальном состоянии при добавлении команд; тест проверяет, что все команды упомянуты и текст влезает в одно сообщение); `/day [дата]` — карточка дня со слиянием по всем голосовым; `/date [дата|сброс]` — рабочий день; `/edit [дата]` — правка расшифровок; `/pending` — записи без даты. Меню команд регистрируется при старте (`SetMyCommands`).

**Рабочий день (`/date`).** `/date 01.09` — все новые голосовые считаются записанными в этот день: «сегодня/вчера» считаются от него, записи о нём — основные (`same_day`), а не «ретро». Хранится в таблице `settings` (ключ `reference_date`), переживает перезапуск, сбрасывается `/date сброс` (или `/date сегодня`). Настройка «липкая» — поэтому каждое подтверждение приёма напоминает о ней. Относится только к новым голосовым, уже сохранённые не меняет.

**Правка расшифровки (`/edit`).** `/edit` — последние 8 голосовых (кнопки: дата, длительность, начало текста, «✎» у уже правленных), `/edit 01.09` — за день. После выбора бот присылает полную расшифровку и меню: «Найти и заменить» (строки `как было => как надо`, также `->` и `→`; регистр не важен; заменяются все совпадения; по каждой строке отчёт, сколько замен), «Заменить целиком» (новый текст одним сообщением, ≤4096 символов — лимит Telegram), «Пересобрать запись» (повторный разбор текущего текста). После правки **прежняя версия расшифровки сохраняется в `transcript_edits`**, а запись пересобирается моделью: `ReplaceExtraction` удаляет прежние извлечения/сегменты/наблюдения этого голосового и создаёт новые. Даты, которые пользователь раньше уточнял кнопками у сегментов этого голосового, при пересборке теряются (бот спросит снова).

**Дневниковая запись в карточке дня.** Если порций несколько, каждая идёт отдельным блоком: «▸ Основная запись · 21:40», «▸ Дополнение · 23:10» (тот же день), «▸ Дополнение из записи от 05.09 · 08:15» (рассказано о дне позже). Единственная основная порция — без заголовка. Остальные текстовые поля помечаются коротко в конце строки, как раньше.

Известные ограничения:
- Очереди и повторных попыток нет; при перезапуске бота идущее распознавание теряется (расшифровка после завершения распознавания уже в БД).
- Текстовый ввод даты («Другая дата») — один слот на чат: если нажать «Другая дата» у нескольких вопросов подряд, ответ уйдёт на последний; прежний вопрос останется без кнопок и доступен через `/pending`.
- Если бот перезапущен, ожидание текстового ввода (дата, замены) теряется: кнопки «Сегодня/Вчера», `/pending` и `/edit` работают заново.
- Замена целиком ограничена лимитом Telegram (4096 символов); правка не меняет `reference_date` уже сохранённого голосового (выбрать другой день для старой записи нельзя).
- Поиск в «найти и заменить» без учёта регистра может задеть лишние вхождения (например, короткие слова): смотрите отчёт о числе замен; прежняя версия текста всегда остаётся в `transcript_edits` (откат — вручную через `make psql`).
- Фильтр YandexGPT может блокировать откровенные темы: явную блокировку бот ловит, вежливый отказ текстом придёт как ответ модели и может не разобраться как JSON (тогда — расшифровка).
- Удаления записей из Telegram нет (только вручную через `make psql`). Повторная обработка **всех** сохранённых расшифровок новым промптом массово не реализована; по одному голосовому это можно сделать через `/edit` → «Пересобрать запись» (данные для неё хранятся: `voice_messages.transcript`, `extractions.prompt_version`).
- Go-клиент использует `HTTPS_PROXY` из окружения; если в нём локальный прокси, запросы к `*.api.cloud.yandex.net` могут зависать (см. «Сеть» ниже) — задаётся `NO_PROXY=.api.cloud.yandex.net` в `.env`.

## Модель данных (реализовано 30.09.2026)
Цель: копить записи в БД, чтобы позже строить статистику и смотреть динамику жизни. Поэтому важно хранить типизированные данные и происхождение каждой порции информации.

**БД: Postgres** (в Docker, наружу не выставляется; Redis для этого не нужен). Схема — `migrations/001_init.sql`, `002_*.sql`.

**Три слоя:** (1) сырой — `voice_messages` (время, расшифровка; аудио не храним); (2) извлечение — `extractions` (JSON модели как есть, версия промпта) и `segments`; (3) `observations` — по строке на каждое упомянутое поле. «Карточка дня» не хранится, её собирает код из наблюдений; правила слияния можно менять задним числом.

**Решения пользователя:**
- Граница «дня дневника» — **05:00 по Москве**: голосовое, отправленное до 05:00, относится к предыдущему дню (`voice_messages.logical_date`). От этой даты модель пересчитывает «сегодня/вчера».
- Если дата записи **неизвестна — бот уточняет** (кнопки в Telegram: «Сегодня / Вчера / Другая дата»). Пока не уточнено, сегмент лежит со статусом `pending_date` и в карточки не попадает.
- **Числовая оценка настроения от модели не нужна** — настроение и всё субъективное хранится текстом.
- Команда **`/day [ДД.ММ[.ГГГГ]]`** показывает собранную карточку дня с пометками происхождения (без аргумента — текущий «день дневника»).

**Вывод модели — JSON** вместо текста; текст для Telegram собирает код. Ответ: `{"segments": [{date, date_source: explicit|relative|unknown, ...поля}]}`, один сегмент на день, о котором говорится в голосовом. Поля: `diary`, `mood`, `food`, `stool`, `sleep_hours` (число), `sleep_quality`, `physical`, `work`, `katya`, `done[]`, `not_done[]`, `water_ml` (число), `sweets`, `alcohol`, `smoking`, `tea`, `gonenie_lysogo`, `love` (bool), `to_think[]`, `for_psychologist[]`. **`null`/отсутствие поля = не упоминалось**, `false` = прямо сказано «нет» (для статистики критично). Ключи JSON намеренно нейтральные (фильтр YandexGPT). Невалидный JSON: один повтор, затем отдаём расшифровку.

**Правила слияния (в коде, не в LLM):**
| Тип поля | Поля | Правило |
|---|---|---|
| Текст | diary, mood, food, stool, sleep_quality, physical, work, katya | дополняется: все порции сохраняются, каждая с источником |
| Список | done, not_done, to_think, for_psychologist | объединение без дублей |
| Число | sleep_hours, water_ml | побеждает самое свежее, при расхождении — пометка конфликта |
| Да/нет | sweets, alcohol, smoking, tea, gonenie_lysogo, love | побеждает самое свежее, при расхождении — пометка конфликта |

**День записи:** `voice_messages.reference_date` — день, к которому голосовое отнесено (выбранный `/date` либо `logical_date`); `logical_date` — день дневника на момент отправки. От `reference_date` зависят «сегодня/вчера» для модели, `relation` (`same_day`/`retro`) и подписи «из записи от …» в карточке.

**Происхождение:** у наблюдения `relation` = `same_day` (голосовое в тот же день дневника, часто второе/третье за день) или `retro` (рассказ о другом дне — «вспомнил позже»). В карточке это видно: «Сон: 6 ч (дополнено из записи от 05.09)».

**Этапы реализации (все сделаны):** (1) Postgres + миграции, сохранение расшифровок до извлечения; (2) JSON-промпт, парсинг, `segments`/`observations`; (3) уточнение даты кнопками; (4) слияние и `/day`; (5) шифрованные бэкапы.

**Бэкапы:** `make backup` → `backups/diary-<время>.sql.gz.enc` (AES-256, пароль `BACKUP_PASSPHRASE` из `.env`; **хранить пароль отдельно от сервера**, иначе бэкапы не расшифровать). `make restore FILE=… DB=…` восстанавливает в новую базу; проверено: число строк в копии совпадает, при неверном пароле недовосстановленная база удаляется. На сервере повесить `make backup` на cron и копировать файлы за пределы сервера.

## Результаты проверки подключения к Yandex Cloud (30.09.2026)
- Проверено руками через curl: Telegram `getMe`, YandexGPT, чтение/запись/удаление в бакете, полный цикл SpeechKit v2 — всё работает.
- **SpeechKit API v2:** `POST https://transcribe.api.cloud.yandex.net/speech/stt/v2/longRunningRecognize` с `config.specification {languageCode: ru-RU, model: general, audioEncoding: OGG_OPUS}` и `audio.uri` = **pre-signed ссылка** на объект в приватном бакете (работает).
